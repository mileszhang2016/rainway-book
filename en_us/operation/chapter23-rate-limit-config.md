# Chapter 23: Rate Limit Policy Configuration

## Chapter Goals

This chapter explains how to create, bind, and verify rate limit policies (RateLimitPolicy) in the Dashboard console and the AI Gateway API. After reading this chapter, readers will be able to:

- Understand the data model of `RateLimitPolicy` and its three rate limit dimensions;
- Master the configuration entry points and submission constraints of the "Rate Limit Configuration" section in the Dashboard;
- Master the configuration methods and parameter semantics of TPM (sliding window), RPM (fixed window), and max concurrency limits;
- Understand the mechanism by which the "Applicable model" is matched by the target model after forwarding;
- Bind rate limit policies to an API-Key or Entity, and understand how Entity-level merging affects the final rate limiting outcome;
- Verify that rate limiting takes effect through BFE configuration, Redis counters, and response behavior.

## The RateLimitPolicy Data Model

A rate limit policy controls the rate at which an API-Key or Entity can access backend AI models, preventing burst traffic from overwhelming upstream services. The Control Plane persists policies in MySQL via the `rate_limit_policies` table; the core fields are documented in `ai-gateway-api/design-docs/sys-design/details/限流策略与导出.md`.

```json
{
  "id": 1,
  "name": "ratelimitX",
  "description": "Default rate limit policy",
  "product_name": "AI_product",
  "enabled": true,
  "max_concurrency": 50,
  "tpm_configs": [
    {
      "name": "tpm_default",
      "model": "*",
      "window_minutes": 1,
      "max_tokens": 100000,
      "step_minutes": 1
    }
  ],
  "rpm_configs": [
    {
      "name": "rpm_default",
      "model": "*",
      "window_minutes": 1,
      "max_requests": 1000
    }
  ]
}
```

The fields are described as follows:

| Field | Type | Description |
|------|------|------|
| `id` | int64 | Unique identifier of the policy in the database; after export it corresponds to `rlp-<id>` |
| `name` | string | Policy name, used only for display in the Control Plane |
| `description` | string | Policy description, making it easier for operators to identify its purpose |
| `product_name` | string | Product line name, currently filled with `AI_product` by default |
| `enabled` | bool | Whether the policy is enabled; disabled policies are not exported to BFE |
| `max_concurrency` | int | Maximum number of concurrent requests; `-1` means no limit, `0` means block, and a positive integer is the concurrency cap |
| `tpm_configs` | array | List of TPM (Tokens Per Minute) rules |
| `rpm_configs` | array | List of RPM (Requests Per Minute) rules |

At the business layer, the Control Plane uses `RateLimitPolicyParam` to carry creation and update parameters, where `TpmConfigs` and `RpmConfigs` are slices of `TPMConfig` and `RPMConfig`, respectively. When exported to BFE, these structures are converted into `BfeRateLimitPolicy`, with a `redis_key` generated by the Control Plane from the rule name.

## Configuring Rate Limit Policies in the Dashboard

The Dashboard provides a "Rate Limit Configuration" section in the creation and edit forms of both Entity organizations and API-Keys (the form as a whole is divided into three sections: Basic Information, Quota Information, and Rate Limit Configuration). The entry points are:

- Consumer Management → Entity Management (organization management) → "Create Entity" or "Edit" in the actions column;
- Consumer Management → API Key Management → "Create" or "Edit" in the actions column.

"Enable Rate Limiting" defaults to "No"; selecting "Yes" expands three sub-sections: TPM rules, RPM rules, and max concurrency. After rate limiting is enabled, at least one valid rule must be configured, and each of the TPM rules and RPM rules allows at most 3 rules.

The applicable scenarios of the three limit types are as follows:

| Type | Applicable Scenario |
|------|------|
| TPM | Control token consumption (long text, scenarios with high inference cost) |
| RPM | Control the number of requests (prevent API abuse, limit QPS) |
| Max concurrency | Control the number of requests processed simultaneously (prevent overwhelming the backend) |

The field semantics and API representation of the three limit types are described below; for how to configure quota information, see [Chapter 22: API-Key and Quota Configuration](./chapter22-apikey-and-quota-config.md).

## Configuring TPM, RPM, and Concurrency Limits

The rate limit policies of the Rainway AI Gateway support three types of limits: TPM (tokens per minute), RPM (requests per minute), and max concurrency. The three can be used individually or combined to meet the dual demands of cost control and stability in different business scenarios.

### TPM Configuration

TPM limits the total number of tokens consumed within a unit time window, and is suitable for scenarios where billing is per token or the backend is sensitive to GPU memory. TPM adopts a sliding window mechanism that smooths token usage statistics over a period of time. Each rule contains:

| Field | Description |
|------|------|
| `name` | Rule name, required, 1–128 characters, must be unique within rules of the same type (TPM); renaming a rule is equivalent to deleting the old rule and adding a new one, and the counter starts over |
| `model` | Applicable model, defaults to `*` (all models); matched by the target model after forwarding — see below |
| `window_minutes` | Time window (minutes), an integer from 1 to 360, default 1 |
| `max_tokens` | Maximum number of tokens allowed within the window, default 10000 |
| `step_minutes` | Sliding step (minutes), an integer from 1 to 360, not exceeding the time window, default 1 |

The plain-language semantics of the three parameters:

- **Time window**: how far back the usage is measured. For example, with a 10-minute window, it measures how many tokens were used in the past 10 minutes;
- **Sliding step**: how often the statistics window slides forward. For example, with a 1-minute step, the total over the past 10 minutes is recomputed every minute;
- **Maximum tokens**: the token cap allowed within the time window; exceeding it triggers rate limiting (returns 429).

For example, time window = 10 minutes, sliding step = 1 minute, and max tokens = 10000 means "check the token usage over the past 10 minutes once every minute, and reject when it exceeds 10000".

> Recommendation: unless you have special requirements, keep the default values (1-minute window, 1-minute step).

The corresponding API representation example (a limit of 100,000 tokens per minute for `gpt-4`):

```json
{
  "name": "tpm_gpt4",
  "model": "gpt-4",
  "window_minutes": 1,
  "max_tokens": 100000,
  "step_minutes": 1
}
```

TPM rules support fine-grained, per-model control: when the target model matches both a specific model rule and the `*` default rule, BFE matches the specific model name first; if no specific model rule matches, it falls back to the default rule.

### RPM Configuration

RPM limits the number of requests within a unit time window, and is suitable for controlling call frequency and preventing script abuse. RPM adopts a fixed window mechanism, counting in cycles of the time window, and **has no sliding step field** — this is the main difference from TPM rules. Each rule contains:

| Field | Description |
|------|------|
| `name` | Rule name, required, 1–128 characters, must be unique within rules of the same type (RPM) |
| `model` | Applicable model, defaults to `*` (all models); matched by the target model after forwarding — see below |
| `window_minutes` | Time window (minutes), an integer from 1 to 360, default 1 |
| `max_requests` | Maximum number of requests allowed within the window, default 100 |

Example: set a limit of 1,000 requests per minute for the default model.

```json
{
  "name": "rpm_default",
  "model": "*",
  "window_minutes": 1,
  "max_requests": 1000
}
```

The RPM and TPM windows can be configured independently. For example, you can configure a 1-minute RPM limit to handle burst traffic while configuring a 60-minute TPM limit to control the overall token budget.

### Concurrency Limit

`max_concurrency` controls the number of requests being processed at the same moment, preventing requests from piling up on the backend due to a large number of long-lived connections. The Dashboard offers three modes:

| Mode | Value | Description |
|------|------|------|
| No limit | `-1` | No concurrency limit; on its own it will not trigger rate limiting |
| Block | `0` | Prohibit all concurrent requests; used to stop all requests in an emergency |
| Limit concurrency | Positive integer | Cap the maximum concurrency; a specific value must be filled in |

Max concurrency is an "auxiliary option" and should be combined with other rules as needed:

- When you only need to control the request rate (e.g., 100 requests per minute), choose "No limit" for concurrency and configure only RPM rules;
- When you also need to control the number of concurrent requests (e.g., at most 10 requests being processed simultaneously), choose "Limit concurrency" and use it together with TPM/RPM;
- "Block" (0) is a shortcut for stopping all requests in an emergency.

Therefore, "No limit" is not "ineffective" — it means placing no concurrency limit and letting TPM/RPM work on their own. For streaming (SSE) scenarios, the concurrency limit is especially important, because streaming requests continuously occupy connection resources.

## Applicable Models Are Matched by the Target Model After Forwarding

The "Applicable model" of TPM/RPM rules is matched by the **target model after forwarding**, not the raw model name in the request body. The target model is the final model name resolved after the request passes, in sequence, through the route "specified model" override, the cluster "trim prefix", and the cluster "model redirect", consistent with the model the backend actually receives. The resolution order is as follows:

1. **Route "specified model" override**: when a request hits a route rule configured with a specified model, the model name in the request body is replaced with that model;
2. **Cluster "trim prefix"**: trim the model name prefix according to the target cluster's configuration;
3. **Cluster "model redirect"**: redirect the model name to another model according to the target cluster's configuration.

Only when none of the above mechanisms is enabled does filling the client's requested model name into "Applicable model" match the old behavior; once redirect, trim, or target override is enabled, you must fill in the forwarded model name for the rules to match correctly. The model access control checks (allowed models / denied models) are likewise performed against the target model after forwarding.

For how to configure the route "specified model" and cluster model mapping (trim prefix, model redirect), see [Chapter 21: Cluster and Route Configuration](./chapter21-cluster-and-route-config.md).

## Creating a Rate Limit Policy

In AI Gateway API, a rate limit policy is usually created together with an API-Key or Entity via the OpenAPI `/api-keys` or `/entities` endpoints, and can also be maintained through a dedicated rate limit policy management API. The following validation rules must be satisfied at creation time; see `ai-gateway-api/design-docs/sys-design/details/限流策略与导出.md` for details:

- `name` is required, non-empty, 1–128 characters long, limited to the character set `[a-zA-Z0-9_-]`;
- `name` must be unique within rules of the same type (TPM or RPM) in the same `RateLimitPolicy`; renaming a rule is equivalent to deleting the old rule and adding a new rule with the same name — the old rule's counter key is cleaned up and the new rule counts from zero;
- `model` must not be empty;
- `window_minutes` is an integer from 1 to 360; `step_minutes` is an integer from 1 to 360 and must not exceed the `window_minutes` of its TPM rule;
- limit fields such as `max_tokens` and `max_requests` must be ≥ 0;
- `max_concurrency`: `-1` means no limit, `0` means block (stop all requests in an emergency), and a positive integer is the concurrency cap.

The following example shows a request body that enables a rate limit policy while creating an API-Key:

```json
{
  "description": "Test Key",
  "rate_limit_policy": {
    "enabled": true,
    "rules": {
      "tpm": [
        {"name": "tpm_1min", "model": "*", "window_minutes": 1, "max_tokens": 10000, "step_minutes": 1}
      ],
      "rpm": [
        {"name": "rpm_1min", "model": "*", "window_minutes": 1, "max_requests": 100}
      ],
      "max_concurrency": 50
    }
  }
}
```

The structure for creating an Entity is the same as above; field definitions can be found in `ai-gateway-api/design-docs/api-define/OpenAPI接口定义/entities.md`. If `rate_limit_policy` is not passed, the system uses the default values: `enabled = false` and an empty `rules`, meaning no rate limiting is applied to the object.

## Binding a Rate Limit Policy to an API-Key or Entity

A rate limit policy is associated with an API-Key or Entity via a foreign key, corresponding to the database fields:

- `api_keys.rate_limit_policy_id`
- `entities.rate_limit_policy_id`

There are two ways to bind:

1. **Bind at creation**: pass `rate_limit_policy` directly in the request body when creating an API-Key or Entity; the system creates the policy and the reference at the same time.
2. **Bind on update**: fully update via `PUT /api-keys/{id}` or `PUT /entities/{id}`, or partially update the `rate_limit_policy` field via `PATCH`.

When a policy's `enabled` is `false`, it is skipped during export to BFE along with its binding, even if it is already referenced by an API-Key or Entity. This design allows operators to temporarily take a policy offline without removing all its references.

Note that deleting an API-Key or Entity cascades deletion of the underlying resources of its dedicated policy, but only when those resources are not referenced by other API-Keys or Entities.

## How Hierarchical Merging Works

The Rainway AI Gateway supports Entity hierarchies; common hierarchy types include organization (org), department (dep), team, and person. When an API-Key is attached to an Entity, its rate limit policies are merged upward along the hierarchy, ultimately forming the complete set of policies that the API-Key must obey.

Rate limiting decision: when a request arrives, BFE collects all policies with rate limiting "enabled" from the API-Key itself, the attached organization, and all ancestor organizations; the request is allowed only if all of them pass, and if any policy is triggered, the request is rate limited (returns 429).

The merging process at export time is as follows:

1. Take the API-Key's own `rate_limit_policy_id`;
2. Recursively collect upward the `rate_limit_policy_id` of the Entity and all its ancestor Entities;
3. Skip policies with `enabled=false`;
4. Generate one binding record for each enabled policy.

The diagram below shows a typical hierarchical merging scenario:

```text
root (ent-root, policy: rlp-0002)
  └─ dep (ent-dep, policy: rlp-0003)
       └─ team (ent-team, no policy bound)
            └─ API-Key ak-test (policy: rlp-0001)
```

For `ak-test`, the final exported binding order is `["rlp-0001", "rlp-0003", "rlp-0002"]`, arranged from itself upward. When a request arrives, BFE checks the rules in these policies in order, and any triggered rule returns 429.

Exported policy names are uniformly `rlp-<policy_id>`, avoiding naming conflicts and making indexing easier for BFE. The Control Plane also generates a Redis Key for each TPM/RPM rule, for example `default_bfe_rlp-1_RL_TPM_rlp-1_tpm_1min`. The key is generated from `(policy_id, rule_name)`, so modifying `model` does not reset the counter, while renaming or deleting a rule cleans up the corresponding old key and adding a rule generates a new key.

If the same policy appears multiple times in the hierarchy, multiple binding records are generated during export; BFE processes or deduplicates them in hit order. It is recommended to avoid binding the same policy repeatedly in Entity design, to reduce configuration volume and troubleshooting complexity.

## Verifying That Rate Limiting Takes Effect

For a policy to take effect, it must go through three stages: "Control Plane export → Conf Agent delivery → BFE hot reload". The verification steps are:

1. In AI Gateway API, confirm that `rate_limit_policy.enabled = true` and that the rule parameters are as expected;
2. Query the exported `rate_limit_policies.json` and `api_key_rl_policy_bindings.json` to confirm the policy and bindings have been generated;
3. In BFE, confirm that `mod_ai_rate_limit` has loaded and has read `ai_rate_limit.data`;
4. Use a load testing tool to send requests at a rate exceeding the RPM/TPM thresholds;
5. Observe the response status codes and changes in the Redis counters.

You can check whether the corresponding counter has been written via Redis, for example:

```bash
redis-cli GET default_bfe_rlp-1_RL_RPM_rlp-1_rpm_1min
```

If the counter keeps increasing and 429 responses are triggered near the threshold, rate limiting is in effect. It is recommended to use a single API-Key and a fixed model during verification, so that concurrent requests from multiple keys and models do not make the results hard to analyze.

## Responses After Rate Limiting Is Triggered

When a request triggers any rate limit rule or exceeds the maximum concurrency, BFE returns `429 Too Many Requests`. After receiving this response, the client should implement backoff retries to avoid further stressing the gateway. Recommended client behavior includes:

- Wait a random amount of time (e.g., 100ms ~ 1s) before the first retry after a failure;
- Use exponential backoff after multiple failures;
- Give up and raise an alert after the retry count reaches the upper limit.

> The current BFE module behavior is governed by the configuration in `bfe/docs/zh_cn/configuration/mod_ai_rate_limit/ai_rate_limit.data.md`; whether the response carries a `Retry-After` header depends on the specific BFE version implementation.

## Complete Configuration Example

Below is a complete rate limit configuration example exported to BFE, usually at the file path `conf/mod_ai_rate_limit/ai_rate_limit.data`:

```json
{
  "Version": "1.0",
  "Config": {
    "AI_product": [
      {
        "cond": "default_t()",
        "hit_action": {
          "cmd": "PASS"
        }
      }
    ]
  },
  "RateLimitPolicies": {
    "rlp-0001": {
      "name": "ratelimitX",
      "enabled": true,
      "rules": {
        "tpm": [
          {
            "name": "tpm_default",
            "window_minutes": 1,
            "max_tokens": 10000,
            "step_minutes": 1,
            "models": ["*"],
            "redis_key": "RL_TPM_rlp-0001_tpm_default"
          }
        ],
        "rpm": [
          {
            "name": "rpm_default",
            "window_minutes": 1,
            "max_requests": 100,
            "burst": 1,
            "models": ["*"],
            "redis_key": "RL_RPM_rlp-0001_rpm_default"
          }
        ],
        "max_concurrency": 50
      }
    }
  },
  "ApikeyRateLimitPolicyBindings": {
    "ak-2v8x9k3m7p": ["rlp-0001"]
  }
}
```

In this example, API-Key `ak-2v8x9k3m7p` is bound to policy `rlp-0001` and is subject to three limits: 10,000 tokens per minute, 100 requests per minute, and a maximum of 50 concurrent requests. In the `Config` section, the `default_t()` condition means the rate limit rule applies to all requests by default, and `hit_action.cmd` being `PASS` means the request is passed to subsequent modules for processing upon a hit.

## Chapter Summary

This chapter covered the complete configuration of rate limit policies in the Rainway AI Gateway:

- `RateLimitPolicy` controls access rate across three dimensions: `tpm_configs`, `rpm_configs`, and `max_concurrency`;
- In the Dashboard Entity/API-Key form "Rate Limit Configuration" section, after selecting "Enable Rate Limiting = Yes", at least one valid rule must be configured, and each of TPM/RPM allows at most 3 rules;
- TPM adopts a sliding window (time window + sliding step), RPM adopts a fixed window (no sliding step); max concurrency: `-1` means no limit, `0` means block, and a positive integer is the concurrency cap;
- The "Applicable model" of TPM/RPM rules is matched by the target model after forwarding, not the raw model name in the request body;
- Policies can be created together with an API-Key or Entity, or re-bound via the update endpoints;
- The Entity hierarchy merges all enabled policies upward — the request is allowed only if all of them pass, and any triggered policy returns 429;
- The Control Plane exports `rate_limit_policies.json` and `api_key_rl_policy_bindings.json` for BFE to consume, and generates a rule-name-based Redis Key for each rule;
- After rate limiting is triggered, BFE returns 429, and the client should retry with backoff logic.

Understanding and correctly configuring rate limit policies is one of the key operations for ensuring the stability of backend AI model services and controlling costs.
