# Chapter 19: Dashboard Basics

## Chapter Goals

Through this chapter, readers will learn how to access the Rainway AI Gateway Dashboard, how its interface is organized, and the basic operation workflow. They will understand the core concepts behind the Dashboard (model provider, AI business cluster, Entity, API Key, route tables, etc.) and be able to complete a first-time configuration independently. Specifically, this includes:

- How to log in to the Dashboard and change the default account;
- The responsibilities of each navigation entry and the data each corresponds to;
- Managing users, roles (system administrator / read-only), Tokens, and permission Scopes;
- The interface differences of the read-only role and the masking rules for sensitive fields;
- General interaction conventions of the Dashboard (drawer forms, view / edit dual mode, notifications);
- The structure and operation of the two operations pages: Batch Tasks and Key Re-encryption;
- The configuration version tracking mechanism;
- How to query data reports (overview + detail tabs) and operation logs (write-operation audit);
- Customizing the console title and icon through `branding/` after deployment;
- The complete first-time configuration flow, from registering an instance pool to the first successful curl call.

## Accessing the Dashboard and the Default Account

The Dashboard is the Admin Console of the Rainway AI Gateway. It calls the OpenAPI v1 interfaces of AI Gateway API through a Web UI to provide visualized management of policies and configurations. After starting AI Gateway API in a local or test environment, you can access the login page in a browser by default at:

```
http://api-server:8183/login
```

Visiting `http://api-server:8183/` directly without logging in also redirects to the login page. Here `8183` is the service port (ServerPort) of AI Gateway API; it can be modified in the `[Server]` section of `conf/ai_gateway_api.toml`. The monitoring port (MonitorPort) defaults to `8284` and is used to expose metrics and health checks; it does not directly serve the console UI.

On first login, the system has a built-in administrator account:

| Item | Default Value |
|------|--------|
| Username | `admin` |
| Password | `admin` |

After a successful login, the Dashboard saves the session key generated by `/auth/session-keys` and carries the authentication information in subsequent requests as `Authorization: Session {session_key}`. In production, the default password must be changed immediately after the first login, and separate accounts should be created for different operators.

### Branding Customization (configurable after deployment)

The titles of the console sidebar, login page, and browser tab, together with the favicon, are controlled by the `branding/` directory in the static output root. Editing it after deployment takes effect without rebuilding the front end:

```
static/
├── index.html
├── static/
└── branding/
    ├── branding.json   // title and favicon configuration
    └── favicon.ico     // site icon
```

```json
{
  "title": "壬远 AI网关",
  "titleEn": "Rainway AI Gateway",
  "favicon": "favicon.ico"
}
```

- `title`: the Chinese UI title; also used as the fallback when another language is not configured;
- `titleEn`: the English UI title; falls back to `title` when empty;
- `favicon`: icon path; relative paths are resolved against the `branding/` directory, and `/xxx.ico` or an `http(s)` address is also accepted; when the referenced file does not exist, no icon is shown.

Refresh the page after editing for the change to take effect; if the browser still shows the old icon, force a refresh or clear the cache. For output acquisition and deployment, see `ai-gateway-web/docs/zh-cn/deploy.md`.

## Dashboard Interface Tour

After logging in, the Dashboard presents a layout of "left navigation + right content area". The navigation is returned dynamically by the `/meta` API, corresponding to the navigation tree defined in `conf/nav_tree.toml`. The main navigation consists of Resource Management, Route Management, Feature Enhance, Consumer Management, System Security, Data Report, User Management, and Operation Logs:

```
AI Gateway
├─ Resource Management
│   ├─ AI Business Clusters        Reference providers, configure forwarding policies
│   ├─ Model Pricing               Model price maintenance and cost accounting
│   ├─ Model Providers             Instance pools, protocols, models, and Keys
│   └─ EPP Scheduling              EPP instance pools and cluster scheduling assignments
├─ Route Management
│   └─ Route Tables                Global / Entity / API-Key routing rules
├─ Feature Enhance
│   ├─ AI Cache Rule               Response cache switch and cache key rules
│   ├─ Traffic Mirror Rule         Async mirroring of production request copies
│   ├─ Intent Config               Question sets and confidence gating thresholds
│   └─ AI Context Compress         Compression rules and global settings
├─ Consumer Management
│   ├─ API Key Management          Issuance and governance of calling credentials
│   ├─ Batch Tasks                 List, details, and cancellation of provider-native batch tasks
│   └─ Entity Management           Types / organizations (quota, rate limiting, model access control)
├─ System Security
│   └─ Key Re-encryption           Batch re-encryption / decryption of sensitive keys in the database
├─ Data Report                     Visualization of operational data: overview metrics, charts, and log details
├─ User Management                 Console accounts and Tokens (administrator)
└─ Operation Logs                  Write-operation audit query (administrator)
```

Each navigation item corresponds to a set of OpenAPI resources:

| Navigation Item | Corresponding OpenAPI Endpoint | Main Responsibility |
|--------|-------------------|----------|
| Model Providers | `/providers` | Maintain model providers, backend instance pools, plaintext API-Keys, and model protocols |
| AI Business Clusters | `/clusters` | Maintain forwarding clusters, LLM configurations, Key weights, and routing policies |
| Model Pricing | `/model-prices` | Maintain model prices under different Providers and time periods, supporting tiered pricing (peak busy hours) |
| EPP Scheduling | `/epp-pool`, `/epp-assignments` | Maintain EPP instance pools and scheduling assignments for EPP-mode clusters |
| Route Tables | `/global-route-rules`, `/route-tables`, etc. | Maintain the three-level global / entity / api-key routing rules |
| AI Cache Rule / Traffic Mirror Rule / Intent Config / AI Context Compress | `/ai-cache-rules`, `/traffic-mirror-rules`, `/intent-config`, `/ai-context-rules` | Maintain response caching, traffic mirroring, intent classification, and context compression policies |
| Entity Management | `/entity-types`, `/entities` | Maintain organization types, organization structures, model allowlists/blocklists, quota and rate limit policies |
| Batch Tasks | `/batches`, `/batch-files/{file_id}` | View provider-native batch tasks and batch file metadata, and cancel tasks |
| API Key Management | `/api-keys` | Create, enable/disable, bind quota, and view keys |
| Key Re-encryption | `/security/reencrypt-sweeps` | Batch re-encrypt / decrypt sensitive key columns and query task history |
| Data Report | `/report/overview`, `/report/timeseries`, `/report/rankings`, `/report/distribution`, `/report/logs` | Visualization queries of operational data; the UI is divided into Overview and Detail tabs (available once `[Report]` is configured; no data otherwise) |
| User Management | `/auth/users`, `/auth/tokens` | Maintain console users and machine Tokens |
| Operation Logs | `/operation-logs` | Read-only audit query of write operations, with change summary and request context |

### General Interaction Conventions

- **List pages**: search area + action buttons + table + pagination; most lists support switching to "20 items/page" (Model Pricing defaults to 50 items/page and supports 20–1000 items/page; Batch Tasks is fixed at 50 items/page with cursor pagination).
- **Drawer forms**: creation / editing is done in a right-side drawer, with "Submit / Cancel" at the bottom ("Next / Previous" for wizard-style forms).
- **View / edit dual mode**: collection-style configurations such as routing rules, AI cache rules, traffic mirror rules, intent config, and AI context compression start in view mode; click "Enter Edit Mode" to add, edit, or delete. Changes are put into the page's draft set with "Save Locally" in the drawer, and only "Submit and Apply" pushes them downstream; after submission the page exits edit mode automatically, and unsubmitted changes do not affect online traffic (see "The View / Edit Dual Mode of Feature Enhance Modules").
- **Notifications**: operation results are shown as notifications in the upper-right corner; error notifications (e.g., "duplicate data") do not auto-dismiss and must be closed by clicking ×.

## Core Concepts in the Dashboard

Many operations in the Dashboard revolve around the following concepts: Provider (model provider), Cluster (AI business cluster), Entity (organization), API-Key, route tables, quota plans, and rate limit policies.

The complete definitions, relationships, and design motivations of these concepts have been introduced together in [Chapter 5: Rainway AI Gateway Architecture and Core Concepts](../design/chapter05-system-architecture.md#core-concepts). This section only explains their corresponding entries in the Dashboard:

| Dashboard Navigation Item | Corresponding Concept | Description |
|---|---|---|
| Resource Management → Model Providers | Provider | Maintain model providers, backend instance pools, model protocols, and authentication keys |
| Resource Management → AI Business Clusters | Cluster | Reference Providers; configure forwarding policies, Key weights, and timeouts |
| Resource Management → Model Pricing | Model Price | Maintain model unit prices under different Providers and time periods (peak busy hours), supporting tiered pricing |
| Consumer Management → Entity Management | Entity | Maintain organization structures, quota, rate limiting, and model access control |
| Consumer Management → API Key Management | API-Key | Issue calling credentials and bind them to Entities |
| Route Management → Route Tables | Route Table | Maintain the three-level Global / Entity / API-Key routing rules |

The above concepts correspond to different stages of the Data Plane request processing order (authentication → model permission → rate limiting → quota → routing → forwarding; see [Chapter 5: Rainway AI Gateway Architecture and Core Concepts](../design/chapter05-system-architecture.md)): API-Keys and Entities carry authentication, model access control, rate limiting, and quota policies; route tables carry routing match rules; Providers and Clusters determine the final forwarding target.

Understanding these concepts is a prerequisite for correctly using the Dashboard. It is recommended to browse the "Core Concepts" section of Chapter 5 before reading this chapter.

## User and Permission Management

Users and permissions of the Dashboard are managed by the `/auth` API family. See `ai-gateway-api/design-docs/api-define/OpenAPI接口定义/auth.md` for the relevant definitions.

### Users

A user is a natural-person account for logging into the Dashboard and comes in two roles: `system_admin` (system administrator with full management permissions) and `system_admin_readonly` (read-only system administrator, who can view all resources but is barred from all write operations, with sensitive key fields displayed masked).

- **Creating users**: "Add User" in the upper-right corner of the "User Management → Users" tab opens the creation drawer with username, password, confirm password, and a "Role" radio group (default "System Administrator").
- **User list**: the "Role" column shows "System Administrator / System Administrator (Read-only)" and supports filtering by role; the operation column provides "Change Role", "Change Password", and "Delete".
- **Changing roles**: in the drawer the target username is read-only and the role is a radio group; submitting calls `PATCH /open-api/v1/auth/users/{user_name}/role` (request body `{"role": "<role>"}`).
- **Built-in account protection**: the built-in `admin` has a fixed role of "System Administrator"; the change-role drawer shows no role radio group and only displays "The built-in account admin has a fixed role of system administrator and cannot be changed"; a downgrade request for it is rejected.

Field constraints when creating a user:

- The username is up to 64 characters and may only contain letters, digits, dots (`.`), underscores (`_`), and hyphens (`-`); it cannot start or end with a dot, underscore, or hyphen; reserved names `admin`, `root`, and `system` are unavailable (constrained only at creation, so they do not block subsequent name-referenced operations such as changing the built-in account's password).
- The password is 8–72 bytes (counted in UTF-8 bytes), cannot contain spaces, and cannot be the same as the username or its reverse.

Administrators can add users, delete users, and reset passwords on the Dashboard under "User Management → Users". When changing your own password, the current password must be entered, and you are automatically logged out after a successful submission; changing another user's password does not require the current password.

### Read-Only Perspective

Logging in with a `system_admin_readonly` account enters the read-only perspective. The read-only role and the system administrator see the **same navigation tree** (`conf/nav_tree.toml` shares one `allowed_roles` configuration between the two roles), so **menus and pages are not trimmed** and every page remains browsable. The differences are limited to:

| Difference | Behavior |
|---|---|
| Write operation buttons | Hidden across the console (trimmed by the front-end `v-has` directive), including "Create / Add / Import" on list pages, "Edit / Delete / Change Role / Change Password" in operation columns, and "Enter Edit Mode / Save Locally / Submit and Apply" on editable pages — the page always stays in view mode |
| In-row and in-drawer write operations | Hidden, e.g. "Reset Quota" for API Key / Entity, "Tiered Pricing Configuration" in the provider list, "Cancel" in the batch task list, and "Trigger Task" in key re-encryption |
| Key-type fields | Key values returned by endpoints that read API Keys, provider service authentication Keys, and Tokens are **masked** by the backend (e.g. `********`); the front end displays them as-is, and a masked value cannot be used for authentication. A system administrator login still receives plaintext |
| Pure read-only modules | Data Report and Operation Logs have no write operations or edit mode; both roles see exactly the same content |
| Retained read-only capabilities | "Details / View" entries and read-only drawers on list pages, search, sorting, pagination, and filter controls, and navigation entries such as "Manage Route Rules" and "Query Model Prices" |

The final line of defense for write capability is the backend: even if the front end is bypassed, write endpoints reject the read-only role (403).

### Session Keys and Tokens

- **Session Key**: generated by `/auth/session-keys` based on the username and password; used for request authentication after logging into the Dashboard, in the format `Authorization: Session {session_key}`. Sessions have an expiration time, controlled by `SessionExpireInDay` by default.
- **Token**: created via `/auth/tokens`; it is the authentication credential for internal programs to access the API Server (the management-plane API service, not the Data Plane forwarding entry). Tokens come in three Scopes, selected as a radio group in the creation drawer and shown with three states in the list and details:
  - **System**: full management permissions over all resources;
  - **SystemReadonly**: read-only access to all resources, equivalent to the read-only administrator role; suitable for programmatic scenarios that only need to view and export;
  - **Support**: can only export data of some resources; suitable for read-only scenarios such as internal operations troubleshooting and data backup; cannot create, edit, or delete any resources.

In production, separate users should be created for Dashboard operators, and dedicated Tokens with the `Support` Scope should be created for machine clients such as Conf Agent, avoiding exposing `System` Tokens directly to the Data Plane.

## Core Module Quick Reference

Each module of the Dashboard is managed through its own list page and form page. Below are the entries and responsibilities of commonly used modules:

| Module Path | List Page Capabilities | Key Operations |
|----------|-----------|---------|
| Resource Management → Model Providers | View Provider list and reference relationships | Create Providers; maintain instance pools / models / Keys |
| Resource Management → AI Business Clusters | View Cluster list and their providers | Create Clusters; configure forwarding policies and Key weights |
| Resource Management → Model Pricing | View model price list | Import / edit model prices; maintain tiered-pricing (peak busy hours) templates |
| Resource Management → EPP Scheduling | View EPP instance pools and cluster assignment relationships | Maintain EPP instance pools; view / override scheduling assignments for EPP-mode clusters |
| Route Management → Route Tables | View the three-level Global / Entity / API-Key route tables | Enable / disable route tables; edit routing rules |
| Feature Enhance → AI Cache Rule / Traffic Mirror Rule / Intent Config / AI Context Compress | View-mode list + edit mode | Enter edit mode to add, edit, or delete; drag rows to reorder; save locally and then submit and apply |
| Consumer Management → Entity Management | View Entity types and organization tree | Create types / organizations; configure quota / rate limiting / model access control |
| Consumer Management → Batch Tasks | Cursor-paginated table (no create entry) | View details; cancel non-terminal tasks |
| Consumer Management → API Key Management | View API Key list and attached organizations | Create Keys, reset quota, view keys |
| System Security → Key Re-encryption | Trigger re-encryption tasks; view the running task and task history | Trigger re-encrypt / decrypt (including dry run); view task details |
| Data Report | Overview tab: 8 metric cards + 7 charts; Detail tab: server-paginated log table (shown once `[Report]` is configured; the menu is hidden otherwise) | Filter reports by time window and dimensions |
| Operation Logs | Filter write-operation audit records by time range and conditions | View the detail drawer (change summary before / after) |
| User Management | View console users and Tokens | Create users, create Tokens, change roles, change passwords |

An example routing rule (JSON view) is as follows:

```json
{
  "enabled": true,
  "rules": [
    {
      "name": "global-default",
      "cond": "default_t()",
      "targets": [
        {
          "cluster_name": "deepseek-cluster",
          "model": "",
          "weight": 100
        }
      ],
      "fallbacks": []
    }
  ]
}
```

Here `cond` is a BFE condition expression; the sum of weights of `targets` within the same rule must equal 100; `fallbacks` specifies degradation targets. Editing routing rules requires entering edit mode first, saving locally, and then submitting to take effect.

## Batch Tasks (Consumer Management → Batch Tasks)

The Batch Tasks page governs provider-native batch tasks created through Data Plane passthrough (OpenAI Batch API: `/v1/files` + `/v1/batches`). The console only governs; it does not create. Batch tasks are initiated by callers carrying an API Key directly against the provider, the Data Plane performs creation rate limiting plus amount reservation / settlement accounting during passthrough, and the console provides listing, details, cancellation, and batch file metadata queries. The entry is "Consumer Management → Batch Tasks" with route `/batches`; the page is a single list page and has **no create entry**.

### Filters and List

The filter bar, from left to right, is: task status (dropdown), provider (input), API Key ID (input; pressing Enter queries), created-after, created-before, "Query", and "Reset". All conditions are optional and combinable (AND).

The table is fixed at 6 columns: Batch Task ID, Status, Request Counts (shows the total / completed / failed of `request_counts`, e.g. `100 / 98 / 2`), Settlement Status, Created At, and Operations ("Details" + "Cancel").

Pagination is **primary-key cursor pagination**: fixed at 50 items per page (not switchable), and the footer only provides "First Page / Previous Page / Page N · M items on this page / Next Page" — there is no total count and no page jump. "Query" and "Reset" both return to the first page; when the last page comes back empty because the previous page happened to be exactly full, the page automatically steps back; paging reuses the conditions of the most recent "Query".

### Status and Settlement Status

| Status Value | UI Text | Terminal |
|---|---|---|
| `validating` | Validating | No |
| `queued` | Queued | No |
| `in_progress` | In progress | No |
| `finalizing` | Finalizing | No |
| `cancelling` | Cancelling | No |
| `completed` | Completed | Yes |
| `expired` | Expired | Yes |
| `failed` | Failed | Yes |
| `cancelled` | Cancelled | Yes |

Settlement status has three states: `reserved` (reserved), `settled` (settled), and `released` (released). The "Cancel" button is disabled for terminal tasks.

### Cancelling a Task

Clicking "Cancel" on a non-terminal task triggers a second confirmation ("Cancel batch task {batchId}? Cancellation calls the provider cancel endpoint and releases the reserved amount."); confirming calls `POST /batches/{batch_id}/cancel` and updates that row's status and settlement status in place without refetching the whole page. Cancellation failure messages: 409 means the task is already terminal or another instance is processing it — refresh the list and trust the server state; 502 means the Control Plane failed to reach the provider over the network (in degraded deployments without egress this capability is unavailable, while listing and details are unaffected); 404 means the task does not exist or has been cleaned up.

### Detail Drawer

"Details" opens a 70%-wide drawer containing 5 cards: Basic Information (Batch Task ID / Provider / API Key ID / Product Name / Entity ID / Passthrough Endpoint), Status and Counts (status Tag + total / completed / failed requests / estimated lines), Usage and Accounting (input and output tokens, usage source, reserved amount, settled amount, settlement status, reservation surplus, sync source), Files and Times (input file ID / output file ID / created / updated / terminal time), and Batch Files (a 6-column table: File ID / Provider / Purpose / File Name / Size / Created At). The drawer is purely read-only and contains no write buttons.

Amount fields (`reserve_units` / `settle_units`) are 1e-8 fixed-point integers in RMB and are displayed as-is without conversion; for tasks sourced from Redis whose job has not yet been persisted, settlement fields may be empty and shown as `-`, which is normal. For the full field and status semantics of batch tasks, see `ai-gateway-web/docs/zh-cn/13-batch-tasks.md`; for the four-dimension batch rate limit configuration, see [Chapter 23: Rate Limit Policy Configuration](./chapter23-rate-limit-config.md).

## Key Re-encryption (System Security → Key Re-encryption)

Key Re-encryption batch re-encrypts / decrypts the sensitive key columns in the gateway database (the `providers` table holding provider service authentication Keys and the `api_keys` table holding API Keys), converging historical data to the current encryption form (the active key of the keyring). The entry is "System Security → Key Re-encryption" with route `/security`.

The page is a single page with three cards:

- **Trigger Re-encryption Task**: three parameters plus a "Trigger Task" button — direction `mode` (`reencrypt` / `decrypt`; the latter is only for rollback plans and must not be triggered in daily operation), scan scope `scope` (all / providers table only / api_keys table only), and dry run `dry_run` (counts the rows "to be rewritten" without writing to the database).
- **Current Running Task**: shows the single running task and its progress; while a task is running the page polls that task every 800ms and updates the list row, this card, and any open drawer in place by `task_id`, without resetting filters, page number, or sorting.
- **Task History**: a filter bar (status / direction / scope / dry run / started-after and started-before) plus a server-paginated table (20 items per page by default, switchable to 20 / 50 / 100); the "Details" action opens a 60%-wide drawer.

Tasks are **cluster-wide singletons**: only one re-encryption task may run at a time, and triggering again while one is running returns 409; the page shows the holder's `task_id` and switches to polling that task directly — **there is no queue**. Task details include the task ID, status, direction, dry-run flag, scan scope, creator, active key ID, start / end times, duration, and per-table statistics (scanned / rewritten / skipped); while running, statistics and duration show placeholder text rather than 0.

This module is a system operations / security feature requiring the `FeatureSecurity` permission (Scope=System): without read permission the API returns 402 (`Feature Access Deny`) and the menu does not appear without the permission. Field-level documentation is in `ai-gateway-web/docs/zh-cn/16-key-reencrypt.md`.

## The View / Edit Dual Mode of Feature Enhance Modules

The four modules under "Feature Enhance" — AI Cache Rule, Traffic Mirror Rule, Intent Config, and AI Context Compress — share one interaction paradigm; understanding it once covers the rest:

| Stage | Behavior |
|---|---|
| Default state | Entering the page gives **view mode**; the table operation column only has "View", and the page header has "Enter Edit Mode" in the upper-right corner |
| Edit state | The header shows "Add Rule" and "Submit and Apply" / "Exit Edit Mode"; the operation column becomes "Edit" and "Delete" |
| Two-step save | "Save Locally" in the drawer only places the change into the page's draft collection (no effect on the live configuration); "Submit and Apply" pushes the whole collection downstream at once |
| Order is priority | Rules are matched in list order and the first match wins; in edit mode you can **drag table rows** to adjust the order (the hint "drag the table to change the effective order" appears below the list), while header sorting only affects display and never the real order |
| Insert position | A new rule is inserted at the head of the collection (highest priority) and the relative order of existing rules is unchanged |
| Exit confirmation | Exiting edit mode with unsubmitted changes prompts "There are unsubmitted changes; exiting edit mode will discard them. Confirm exit?"; confirming rolls back to the snapshot taken on entering edit mode, while cancelling stays in edit mode and keeps the changes |

The route table's edit mode additionally provides an in-row "Copy" action for quickly deriving a similar rule. Field semantics of the four collection-style configurations are documented in `ai-gateway-web/docs/zh-cn/08-ai-cache-rules.md`, `09-traffic-mirror-rules.md`, `10-intent-config.md`, and `11-ai-context.md`.

## Configuration Version Tracking Mechanism

Rainway AI Gateway adopts a configuration export mechanism based on MD5 signatures and version numbers. See [Chapter 14: Configuration Export and Version Control Design](../design/chapter14-config-export-and-version-control.md) for the detailed design. The Control Plane maintains a current version number and signature for each configuration topic (Topic), such as `route_rule`, `ai_route`, `mod_api_key_rule`, etc.:

- **Current version number**: format `YYYYMMDDHHMMSS`, e.g. `20260102120000`;
- **MD5 signature**: computed over the configuration content with the version number zeroed out;
- **Last change time**: any signature change is regarded as one effective configuration change.

This mechanism guarantees that: if the configuration content has not changed, Conf Agent receives `Data: null` when pulling, avoiding meaningless hot reloads; once the content changes, the Control Plane generates a new version number and returns the full configuration, and BFE completes the hot update accordingly. Configuration version information is mainly exposed to Conf Agent and operations troubleshooting tools via InnerAPI. The Dashboard currently focuses on resource management; for version details, refer to the Control Plane logs or the InnerAPI export interfaces.

## Complete First-Time Configuration Flow via the Dashboard

Below is a minimal configuration flow from an empty environment to the first successful call, corresponding to the real navigation entries of the Dashboard. For more detailed field descriptions and example values, refer to the Dashboard user manual `ai-gateway-web/docs/zh-cn/19-scenarios.md` (Scenario Walkthrough).

### Step 1: Log In and Change the Default Password

After logging in with the default account `admin/admin`, go to "User Management → Users", change the `admin` password to a strong password, and create other administrator accounts as needed by the team (choosing the "System Administrator" or "System Administrator (Read-only)" role).

### Step 2: Create a Model Provider

Go to "Resource Management → Model Providers" and click "Create Provider":

- Name: the unique identifier of the Provider, e.g. `demo-provider`;
- Instance pool: the IP / port / weight of the backend model service (fill in 100 for a single instance), e.g. `172.19.1.187:13801`;
- Model protocol: e.g. `openai`;
- Service authentication Keys: fill in the Key name and plaintext if the backend requires authentication;
- Model list: click "Fetch" to pull the available models and select, e.g. `doubao-pro-32k`.

After creation succeeds, the Control Plane automatically generates backend instance pools and sub-clusters based on the instance pool.

### Step 3: Create an AI Business Cluster

Go to "Resource Management → AI Business Clusters" and click "Create Cluster"; complete the wizard step by step:

1. **Basic configuration**: fill in the cluster name (e.g. `demo-cluster`), protocol (e.g. `https`), and whether to enable session persistence;
2. **Timeout and retransmission**: usually keep the recommended defaults;
3. **Passive health check**: usually keep the default;
4. **LLM configuration**: select the Provider created in the previous step (e.g. `demo-provider`), check the models allowed for forwarding (e.g. `doubao-pro-32k`), and reference the Provider Keys with weights as needed;
5. **Review and check**: verify the summary and click "Submit"; the new cluster appearing in the list indicates successful creation.

### Step 4: Create an Entity Organization (Optional)

If you need to configure quota, rate limiting, or model access control uniformly by organization, go to "Consumer Management → Entity Management":

- First create an Entity type (e.g. `team`, level 3);
- Then create an Entity organization (e.g. `dev-team`), keep allowed models as `*`, and bind the quota plan, rate limit policy, and model allowlist/blocklist as needed.

### Step 5: Issue an API Key

Go to "Consumer Management → API Key Management" and click "Create":

- Description: the identifier of the API Key (e.g. `demo first Key`);
- Owning Entity: select the Entity created in Step 4 (optional; leave empty if Step 4 is skipped);
- Expiration time: check "never expires" or specify as needed;
- Allowed subnets: default `*` (no restriction);
- Allowed models: fill in as needed.

After creation succeeds, the Key value of this API Key is displayed in masked form in the list (first 8 characters + `****` + last 4 characters); click the Key value to view the full plaintext and copy it with one click — keep it safe. Also record the Key ID of this Key (e.g. `api-key-1`): in the next step you will use the Key ID to find the corresponding apikey route table. The Key value cannot be modified after creation.

### Step 6: Configure API-Key Routing Rules

Go to "Route Management → Route Tables", find the `apikey` route table whose owner is the Key ID from Step 5, enter edit mode, and add a rule. For example:

```json
{
  "enabled": true,
  "rules": [
    {
      "name": "demo-default",
      "cond": "req_path_prefix_in(\"/\", false)",
      "targets": [
        { "cluster_name": "demo-cluster", "model": "doubao-pro-32k", "weight": 100 }
      ],
      "fallbacks": []
    }
  ]
}
```

Save locally and then click "Submit and Apply"; nothing affects online traffic until it is submitted.

### Step 7: Verify the Configuration Takes Effect

After completing the above steps, verify as follows:

1. Trigger a Conf Agent pull or wait for its scheduled polling, and confirm that BFE has completed the hot reload;
2. Send a request with curl to verify that traffic is forwarded to the target cluster according to the rules:

```bash
curl -H "Authorization: <API Key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"doubao-pro-32k","messages":[{"role":"user","content":"hello"}]}' \
  http://<bfe-address>:8080/v1/chat/completions
```

## Reports and Usage Analysis

The Dashboard has a built-in Data Report module that provides administrators with a unified visualization view of operational data: overview metric cards, timeseries line charts, dimensional rankings, proportion distributions, and log details — no additional Grafana deployment required. The reports consume the `/open-api/v1/report/*` APIs and require the reporting form to be configured as described in "Chapter 18: Installation and Deployment": the lightweight form (`[Report].Backend = "mysql"` plus the log-reader `mod_log_mysql` plugin) or the standard form (`Backend = "doris"` / `clickhouse` / `starrocks` with the Kafka pipeline). Once `[Report]` is configured, the Dashboard shows the Data Report menu; without it, the module stays unassembled, the menu does not appear, and the APIs return 404.

### Page Structure

The report page is divided into a **global filter bar** and a **tab area**:

- **Global filter bar**: two rows. The time area provides quick time buttons (1 hour / 6 hours / 24 hours / 7 days), start and end time pickers, and a "Latest" button; the dimension area provides 6 general filters (target model, API Key, provider, Host, stream, status code), with the "Split Dimension" dropdown and the "Query" / "Reset" buttons at the end of the row.
- **Tabs**: divided into the **Overview** and **Detail** tabs; filters are shared across tabs and persist when switching.

Key behaviors of the two areas:

- **Quick time**: clicking sets the end time to now and the start time to "now − span", then queries immediately; manually changing start or end removes the highlight from the quick buttons.
- **"Latest"**: keeps the current span and shifts the whole window to the current moment before re-querying.
- **"Reset"**: clears the 6 general filters and restores "Split Dimension" to "No split", then re-queries, but **does not change the time range** or the quick-button highlight (so two clicks on the same button never disagree); use the quick buttons to return to the default window.
- **Target model** (`models`) filters on the routed target model; values come from the models each cluster actually supports (`llm_config.models`) and exclude model names that only appear as request aliases. The values of the other dimension dropdowns are populated dynamically from the ranking API for the current time window.
- **"Split Dimension"**: options are no split / cache status / mirror hit / intent answer. It is **not a query filter**; it only decides whether the QPS / Token / latency timeseries charts are split into multiple series by dimension bucket, and does not affect the metric cards, the ranking / proportion / distribution charts, or the detail table. Selecting an option takes effect only after clicking "Query".

### Overview Tab

The Overview tab shows **8 metric cards** (total requests, total errors, token usage, average latency, cost, cache hit rate, mirror hits, intent classifications) and **7 charts** (QPS timeseries, token timeseries, latency timeseries, ranking, proportion, distribution, cache token timeseries) within the selected time window. The sampling interval of timeseries data is computed by the server based on the window, so the client passes no parameters; cost data is displayed separately by currency — the main value of the overview card takes the first currency (amount + currency in small text), the remaining currencies are listed as secondary rows, and "-" is shown when there is no cost data. The ranking, proportion, and distribution charts each have a dimension dropdown next to the card title; switching it refetches with the new dimension immediately (no "Query" click needed).

> Latency percentiles are returned only by the standard-form backends (Doris / ClickHouse / StarRocks); the UI always shows only the average and maximum, and the MySQL lightweight form has no native percentiles.

### Detail Tab

The Detail tab shows a **server-paginated log table**:

- **20** items per page by default (switchable to 20 / 30 / 40 / 50), ordered by time descending (latest requests first);
- A fixed set of 15 columns: time, API Key, requested model, target model, provider, status code, duration, tokens, TTFT, cost, cache, mirror, intent answer, error, operations;
- A toolbar with 8 filters that only affect the log table query: requested model (`requested_models`), error only (`err_only`), keyword (fuzzy match on the error message, max 128 characters), cache status (`hit` / `miss` / `skip`), mirror hit, intent question, intent answer (including `unknown`), and intent source (`explicit_header` / `classifier` / `cache`);
- The "Details" action opens a right-side drawer showing logid, log time, host, product line, API / requested model / target model / provider, protocol and mode, stream flag, status code and error code, error message, input / output / total tokens, duration, TTFT, TPOT, cost, label levels, client IP and Host, original URI, cache status, mirror hit (with the mirror cluster), and intent question / answer / confidence / source / latency / cache hit / version, with four collapsible JSON areas at the bottom: `ai_rate_limit_hits`, `ai_auth_reject_quota_plans`, `req_headers`, and `res_headers`.

### API-Level Views

Behind the report tabs, the APIs are still organized into the following five views, facilitating automation and secondary development:

| View | Content | API |
|------|------|------|
| Overview | Total requests, error rate, token totals, average latency, TTFT/TPOT, cost (by currency), cache hit rate, mirror hits, intent classifications | `GET /report/overview` |
| Time series | Bucketed curves for QPS, token throughput, latency, TTFT/TPOT, cost growth rate, and cache tokens; time buckets adapt to the window (1-minute buckets within 6h), and `dimension` supports splitting by `ai_cache_status` / `mirror_hit` / `ai_intent_answer` | `GET /report/timeseries` |
| Rankings | TopN request-count rankings by model, provider, API Key, host, status code, protocol, mode, cache status, mirror hit, intent answer, etc. | `GET /report/rankings` |
| Distribution | Proportion pie charts for status code, protocol, mode, stream, cache status, mirror hit, and intent answer | `GET /report/distribution` |
| Log details | Per-request details with filters for requested model, error only, error keyword, cache status, mirror hit, and intent question / answer / source, ordered by time descending with pagination | `GET /report/logs` |

Usage notes:

- **Time window**: all views share the time picker; the maximum window is 7 days (aligned with the detail retention period). For ranges beyond 7 days, query in segments via the filter bar: counting metrics can be summed, while averages and proportions cannot.
- **Permissions**: reports are an administrator feature requiring `FeatureReport + ActionReadAll`; the `system_admin` and `system_admin_readonly` roles and Tokens with the `System` and `SystemReadonly` Scopes all qualify.
- **Form differences**: the MySQL lightweight form does not provide P50/P90/P99 percentile latency, and no percentile metric is displayed; the standard form shows full percentiles. If percentile latency is required, use a standard-form backend.
- **Consistent definitions**: report metrics are derived from the same source as the existing Grafana Dashboard panels, so the two views reconcile under the same data source.

## Operation Logs and Audit

The Operation Logs module (sidebar "Operation Logs") provides a **read-only audit query** of platform write operations. Logs are written automatically by the system when configuration changes occur; the console provides no manual entry interface, and system administrators (including the read-only role) can access it.

### List Page

The page is divided into a **time filter bar** and a **paginated table**:

- **Time range filter**: set the start time and end time and click "Query" to filter logs by closed interval; when no time is set, all logs are shown (subject to pagination).
- **Table columns**: Operator (fuzzy search; the console user or Token name that performed the operation), Action (dropdown; `create` / `update` / `delete` / `reset` / `import` / `bind` / `unbind`, etc., shown as Tags), Resource type (dropdown, displayed with Chinese labels), Resource name (fuzzy search), Result (success / failure), Operation time (format `YYYY-MM-DD HH:mm:ss`), and a "Details" button in the operation column.
- **Resource type labels**: both the dropdown and the column use Chinese labels — Entity, Entity Type, API Key, Provider, Cluster, Route, Certificate, Quota Plan, Model Pricing, Batch Task (`batch`), Batch File (`batch_file`), User, and Token.
- **Pagination**: this module uses server-side pagination (20 items per page by default, with switchable page number and page size), unlike the frontend pagination used by some modules.

### Detail Drawer

Click "Details" in the row operation column, and a detail drawer slides out from the right, showing the operator type (User / Token), operator, action, resource type, resource ID, resource name, parent resource ID, result, error message (shown only on failure), change summary, request path and method, client IP, User-Agent, and operation time. The **change summary** can be expanded to view the `before` / `after` JSON comparison and diff fields; sensitive fields are masked.

### Log Sources and Permissions

The following write operations automatically produce operation logs on success or failure: Entity / Entity types, API-Keys, model providers, business clusters, route tables, certificates, quota plans, model pricing, console users and Tokens, and batch tasks (task cancellation, `resource_type=batch`). A typical usage is to return to Operation Logs after making configuration changes in other modules and search by resource name or time range to verify the change content and the operator.

Without read permission, the API returns `Feature Access Deny` (402) and the list fails to load; if you cannot see the "Operation Logs" menu, confirm that the account has the corresponding feature permission.

## Operational Notes

When using the Dashboard for daily operations, keep the following in mind:

1. **Default account security**: `admin/admin` is only for the first login; in production the password must be changed immediately and access sources must be restricted. The built-in `admin` has a fixed role of "System Administrator" and cannot be changed.
2. **Permission model**: console users come in two roles, `system_admin` (system administrator) and `system_admin_readonly` (read-only system administrator). The navigation and pages of the read-only role are not trimmed, its write buttons are hidden, all write endpoints return 403, and sensitive fields such as API-Keys, Provider Keys, and Tokens are masked in both the UI and API responses. Tokens are divided into `System` (full management permissions), `SystemReadonly` (read-only over all resources), and `Support` (read-only export permissions); prefer the `Support` Scope when creating Tokens for Conf Agent or automation scripts.
3. **Password and username constraints**: the password is 8–72 bytes (in UTF-8), cannot contain spaces, and cannot be the same as the username or its reverse; the username is up to 64 characters, and the reserved names `admin`, `root`, and `system` cannot be created.
4. **Cascading impact of Provider changes**: modifying a Provider's instance pool, Keys, or model list triggers a synchronized update of the Clusters referencing it; before deleting a Provider, make sure no Cluster references it, otherwise a `409 Conflict` is returned.
5. **Reference check on Cluster deletion**: before deleting a Cluster, the system checks whether it is referenced by Global / Entity / API-Key routing rules; if referenced, the references must be removed or the rules modified first.
6. **Two-step save for collection-style configurations**: route tables, AI cache rules, traffic mirror rules, intent config, and AI context compression all require "Enter Edit Mode → Save Locally → Submit and Apply". Unsubmitted changes do not affect online traffic; a new version is generated and triggers a Conf Agent pull only after submission.
7. **Configuration propagation delay**: after a change in the Dashboard is written to MySQL, it takes effect only after Conf Agent pulls it and triggers a BFE hot reload. Do not expect a configuration to take effect on the Data Plane immediately after saving.
8. **Only a version number change represents a real change**: even if you click save many times, as long as the MD5 signature of the configuration content does not change, the version number in `config_versions` does not increase, and the Data Plane does not reload.
9. **API-Key masked display**: in the API Key list, the Key value is displayed masked (first 8 characters + `****` + last 4 characters) and can be clicked to view and copy the full value; however, the Key value cannot be modified after creation, so keep it safe immediately after creation succeeds.
10. **Operation logs are read-only audit records**: operation logs are recorded automatically by the system on write operations and can only be queried — no modification or deletion entry is provided; to verify historical changes, search the Operation Logs by resource name or time range.

## Chapter Summary

This chapter introduced the basic operations of the Rainway AI Gateway Dashboard. The main contents include:

- The Dashboard is accessed by default at `http://api-server:8183/login`, with the initial account `admin/admin`; the title and icon can be customized after deployment through `branding/branding.json` in the deployment directory;
- The console has a "left navigation + right content area" layout, covering Resource Management (Model Providers, AI Business Clusters, Model Pricing, EPP Scheduling), Route Management, Feature Enhance, Consumer Management (Entity Management, Batch Tasks, API Key Management), System Security (Key Re-encryption), Data Report, User Management, and Operation Logs;
- Model providers, AI business clusters, model pricing, Entity organizations, API Keys, and route tables are the core concepts of the console; understanding their responsibilities and reference relationships is a prerequisite for correct configuration;
- The console adopts common interactions such as drawer forms, list pages, and view / edit dual mode; collection-style configurations must be saved locally and then submitted, and in edit mode rows can be dragged to reorder — order is priority;
- User roles are `system_admin` / `system_admin_readonly`, and both user creation and role changes are done in the UI (the built-in `admin` role is fixed); the read-only role keeps all menus and pages but hides write buttons and masks keys; Tokens come in three Scopes: `System`, `SystemReadonly`, and `Support`;
- The Batch Tasks page lists provider-native batch tasks with cursor pagination and provides filters, a detail drawer, and cancellation (not available for terminal tasks), with no create entry;
- The Key Re-encryption page organizes triggering, the running task, and task history into three cards; tasks are cluster-wide singletons and a repeated trigger while one is running returns 409;
- Configuration versioning is based on MD5 signatures and `YYYYMMDDHHMMSS` version numbers, enabling incremental synchronization, and is mainly exposed to InnerAPI and Conf Agent;
- The first-time configuration should follow the order "model provider → AI business cluster → Entity (optional) → API Key → routing rules → curl verification";
- The Data Report module provides two tabs — Overview (8 metric cards + 7 charts) and Detail (server-paginated log table) — with quick time buttons, the "Latest" window shift, and "Split Dimension" for the timeseries charts; it is available only after `[Report]` is configured and a reporting form is deployed;
- Operation Logs perform read-only auditing of platform write operations, showing resource types with Chinese labels and supporting time range filtering plus a detail drawer with a change summary (before / after JSON, with sensitive fields masked);
- Daily operations require attention to default account security, cascading reference checks, two-step saving, configuration propagation delay, and the principle of least privilege for Tokens.

After mastering this chapter, readers can complete the initialization and basic management of the Rainway AI Gateway in the Dashboard, laying a foundation for the specialized configuration topics in subsequent chapters, such as Providers, Clusters, API-Keys, and rate limiting.
